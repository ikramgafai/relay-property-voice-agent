# Relay v0.10.0 — Real-Time Barge-In & Transaction-Safe Interruption

A caller can now interrupt Relay. When they start speaking while Relay talks, Relay's voice stops
and their utterance becomes the next normal turn. Interruption affects speech only: committed
business results are never rolled back.

## Added

- **Barge-in.** Caller speech interrupts the active Relay speech through a provider-neutral
  `SpeechPresentation.interrupt()`, requested by `RealtimeSession` before `USER_SPEECH_STARTED` is
  emitted.
- **Cooperative, generation-fenced output interruption.** Only outputs that exist when the
  interrupt is requested are affected. The TTS producer is cancelled, Python-side frames are
  discarded and LiveKit's native queue is cleared (`AudioSource.clear_queue()`); a blocked
  `capture_frame()` is never intentionally cancelled, and is allowed to return before a second
  clear.
- **Reusable output transport.** After a normal interruption the same `SpeechOutput` and LiveKit
  sink speak the next response.
- **One barge-in request per provider turn.** `SPEECH_STARTED` is the primary trigger, the first
  partial of a newer provider turn the fallback; repeat, late or stale signals are ignored.
- **`USER_INTERRUPTED`.** Interrupted outputs report `AGENT_AUDIO_OUTPUT_ENDED` with status
  `CANCELLED` and code `USER_INTERRUPTED`. No new event type.
- **STT speech-start diagnostics.** Counts-and-timings logs for raw provider speech starts, Turn
  arrivals and provider events, never transcript text.

## Reliability

- Barge-in never cancels the business turn, calls turn cancellation, or changes bindings, workflow
  state or tool results.
- A pending output that existed at the interrupt never reaches the TTS provider.
- An interrupted TTS producer that is slow to stop stays owned and cannot queue audio; session
  close cancels it.
- A failed native clear is logged; if the in-flight capture then fails, output is reported
  unavailable rather than silently reused.

## Changed

- A provider speech-start signal for a provider turn that has already reached FINAL no longer
  emits `USER_SPEECH_STARTED`, so a delayed signal cannot interrupt the response to that same turn.

## Validation

- 569 automated tests (PostgreSQL + LiveKit in Docker), 12 browser audio tests, strict mypy and
  Ruff clean.
- **Real-microphone Gate A (instrumented rerun): PASS.** Quick audible cutoff, the complete
  interrupting sentence admitted, the next response spoken on the same sink. A first attempt
  failed (late cutoff, interrupting sentence reduced to "Instead." by the provider) and led to the
  timing instrumentation.
- **Transactional Gate B: PASS.** An emergency incident was committed, its spoken confirmation was
  interrupted 2.86 s later, and the interrupting hazard updated the **same** incident (revision
  1 → 2): one create and one update, each attempted once and never replayed, no duplicate
  incident, no rollback.

## Known limits

- AssemblyAI reported speech about 1.4–1.5 s after onset in the successful live runs; that
  provider latency dominates barge-in latency. Faster local voice-activity detection is not
  implemented.
- Live coalescing of two provider finals into one turn is still not directly observed.
- Open-microphone and background-speech hardening remains future work.
- This is a validated engineering milestone on a local stack, not a production-ready voice
  platform; demo endpoints are not hardened for public use.
